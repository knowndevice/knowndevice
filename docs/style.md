# Writing rules

Write for the person who needs to use or change the software. Use English
in public docs, code comments, CLI output, issues, and release notes.
Maintainer prompts and work conversations may be in Polish.

Start with the concrete behavior or decision. Use familiar words, active
verbs, and short connected paragraphs. Use a list for actual steps or
parallel items, and a table for comparisons. Explain domain terms once.

Avoid promotional filler, repeated summaries, artificial questions and
answers, exaggerated certainty, and empty claims about quality. Do not
call the project seamless, revolutionary, enterprise-grade, production-ready,
or secure by design without a scoped, supported meaning. Ban AI slop across
docs, comments, issues, commits, and UI copy.

Describe implemented and planned behavior separately. A planned feature
gets a status and milestone, not present-tense availability. Cite current
primary sources for external facts. Mark inference and unmeasured targets.
Never invent a test result, operator, installation, benchmark, or approval.

Do not add tool authorship credits, generated-by banners, assistant
co-author trailers, or promotional references to development helpers.
Keep required human DCO sign-offs and third-party license notices. Tool
names belong in contributor configuration or integration documentation
when they help someone use that configuration.

Automated checks catch a short list of obvious phrases and attribution
banners. Human review still checks clarity, repetition, evidence, and tone.
Technical terms inside standards, licenses, source titles, or quoted errors
are not rewritten to satisfy a word filter.
